# 数学一知识点库 Final —— 代码生成 AI 交接提示词

> 用途：把本提示词连同以下 3 个文件一起交给负责开发题库/学习系统的代码生成 AI。  
> 目标：让对方准确理解这些文件是什么、为什么存在、应该如何使用，以及后续代码应该围绕它们完成什么工作。

---

## 一、你的角色

你现在接手的是一个 **考研数学一题库系统的知识点基础设施**。

请先完整理解本提示词和附带的知识点文件，再开始写代码。

你的任务不是重新设计数学知识体系，也不是自行重新拆分知识点，而是：

1. 正确读取现有知识点库；
2. 将知识点作为题库系统中的稳定基础数据；
3. 建立“题目 ↔ 知识点”的多对多关联；
4. 支持核心知识点、辅助知识点、别名搜索、章节筛选、统计分析等功能；
5. 后续允许在版本升级时新增/合并知识点，但不能随意破坏现有 ID 和数据关系。

---

# 二、项目背景

这套知识点库服务于 **考研数学一**。

它不是直接照搬教材目录，也不是只按照考试大纲的大章节划分，而是专门为了“题库绑定”设计的。

## 核心拆分原则

知识点粒度遵循：

> **一个知识点尽量对应一类稳定题型，或一种稳定解题方法。**

例如：

- 不使用过粗的 `曲面积分`
- 而拆成：
  - `第二类曲面积分直接投影法`
  - `三合一投影法`
  - `普通高斯公式`
  - `高斯公式补面法`
  - `有瑕点的高斯公式`
  - `第一类斯托克斯公式`
  - `第二类斯托克斯公式`
  - `斯托克斯公式换面法`

同一道题可以绑定多个知识点。

例如一道题可能绑定：

- core：`有瑕点的高斯公式`
- auxiliary：`第二类曲面积分方向判断`
- auxiliary：`第二类曲面积分对称性`

不要为了每一种组合重新制造新的知识点。

# 三、这套知识点库是怎么产生的

这套库不是一次性由 AI 凭经验生成的。

整个过程经过了多轮校准：

1. 以 **2026 考研数学一考试大纲** 作为考试范围边界；
2. 第一轮按高等数学、线性代数、概率论与数理统计拆成末级知识点；
3. 对过粗、过细、重复的知识点重新合并和拆分；
4. 使用 **1987—2026 共 40 届数学一真题** 逐年反向扫描；
5. 检查每道真题是否能被现有知识点自然覆盖；
6. 真题无法准确覆盖时，才考虑新增知识点；
7. 两个标签长期高度重复时进行合并；
8. 某些知识点如果更多只是辅助工具，则调整默认角色；
9. 2024、2025、2026 最新三届真题再次复核后，知识点体系基本闭合。

因此，这份 Final 版本的价值在于：

> **它不是教材目录，而是经过 40 届真题验证的“题型级知识点字典”。**

# 五、你会收到的三个文件

## 1. `math1-knowledge-final.json`

### 这是最重要的文件，也是程序端的主数据源。

建议：

> **JSON 作为系统中的 Source of Truth。**

每个知识点大致结构：

```json
{
  "id": "M1-H06-035",
  "name": "有瑕点的高斯公式",
  "aliases": [
    "有奇点的高斯公式",
    "挖洞高斯",
    "挖球法",
    "去奇点高斯"
  ],
  "subject": "数学一",
  "section": "高等数学",
  "chapter": "多元函数积分学",
  "default_role": "core",
  "status": "active"
}
```

### 字段含义

#### `id`

知识点唯一 ID。

格式示例：

```text
M1-H06-035
```

含义：

```text
M1 = 数学一
H  = 高等数学
L  = 线性代数
P  = 概率论与数理统计
06 = 对应章节
035 = 章节内知识点编号
```

**非常重要：ID 是知识点真正的数据库身份。**

以后题目绑定知识点时：

> 必须存 `knowledge_id`，不能只存知识点名称字符串。

名称以后可以改，但 ID 不应因为显示名称修改而改变。

---

#### `name`

知识点唯一标准名称，即 canonical name。

例如：

```text
有瑕点的高斯公式
格林公式补线法
全期望公式
矩阵可相似对角化判定
非正则情形最大似然估计
```

所有正式展示、统计、关联均优先使用 `name`。

---

#### `aliases`

知识点别名。

例如：

```json
{
  "name": "有瑕点的高斯公式",
  "aliases": [
    "有奇点的高斯公式",
    "挖洞高斯",
    "挖球法",
    "去奇点高斯"
  ]
}
```

作用：

- 搜索；
- 自动打标签；
- 兼容不同老师/教材叫法；
- 避免把同一个知识点重复创建成多个节点。

**不要把 alias 再创建成一个新的知识点。**

---

#### `subject`

当前均为：

```text
数学一
```

以后系统如果扩展数学二、408、英语、政治，可以沿用同一结构。

---

#### `section`

一级学科模块：

```text
高等数学
线性代数
概率论与数理统计
```

---

#### `chapter`

章节分类，例如：

```text
函数、极限与连续
多元函数积分学
特征值与特征向量
参数估计
```

注意：

> section / chapter 主要用于分类展示，不是题目最终绑定的最小知识点。

题目真正绑定的是 `id + name` 对应的末级知识点。

---

#### `default_role`

取值：

```text
core
auxiliary
```

含义：

### `core`

通常能够作为一道题的主要考查对象。

例如：

```text
泰勒展开求极限
普通高斯公式
矩阵可相似对角化判定
全概率公式
最大似然估计
```

### `auxiliary`

通常作为另一知识点的辅助工具、条件或性质。

例如某些方向判断、基础性质等。

但请注意：

> `default_role` 只是知识点的默认角色，不应该把它写死成“永远只能是 core / auxiliary”。

具体到一道题时，题目关系表中的 `role` 可以覆盖默认角色。

例如 `全期望公式` 在某一道题里完全可以是 core。

---

#### `status`

当前正式知识点均为：

```text
active
```

未来如需废弃知识点，建议使用：

```text
deprecated
```

而不是直接从数据库物理删除。

这样不会破坏历史题目关联。

---

## 2. `math1-knowledge-final.md`

### 这是给人阅读和审查的版本。

它按章节把 469 个知识点完整列出，并包含：

- ID
- 知识点名称
- 默认角色

主要作用：

1. 人工快速检查知识点体系；
2. 产品/运营/教研人员查看；
3. 开发阶段对照 JSON；
4. 调试题目标签时人工核对；
5. 做后台管理页面时作为结构参考。

它不是程序运行时的最佳数据源。

程序端仍应优先使用 JSON。

---

## 3. `math1-knowledge-final.csv`

这是平面化数据版本。

主要价值：

- Excel 检查；
- 数据库批量导入；
- SQL / DataFrame 批处理；
- 人工修改和筛选；
- 后台运营导入导出。

如果要初始化数据库，可以直接读取 CSV 或 JSON。

但系统运行时仍建议最终把知识点持久化到数据库。

# 六、这套知识点库解决什么问题

普通题库往往只有：

```text
科目：数学一
章节：概率论
```

这种标签太粗。

这套知识点库希望做到：

```text
题目
├─ 正态随机变量线性组合
├─ 协方差计算
└─ 二维正态下不相关等价于独立
```

这样系统以后就能够实现：

### 1. 精准刷题

用户可以直接选择：

```text
只刷：有瑕点的高斯公式
```

而不是只能：

```text
刷：多元积分
```

---

### 2. 错题诊断

如果用户连续做错：

```text
格林公式补线法
有瑕点的格林公式
有瑕点的高斯公式
```

系统可以判断：

> 用户的“闭合区域 / 去奇点”类处理能力存在明显薄弱点。

---

### 3. 知识点掌握度

可以为每个知识点维护：

```text
attempt_count
correct_count
accuracy
last_attempt_at
mastery_score
```

---

### 4. 真题统计

知识点与真题绑定后，可以自动统计：

```text
历史出现次数
近10年出现次数
近5年出现次数
选择题出现次数
填空题出现次数
解答题出现次数
```

不要人工给知识点写：

```text
★★★★★
高频
低频
```

更推荐由真实题库数据动态计算。

---

### 5. 自适应刷题

后面可以根据：

```text
用户知识点掌握度
+
题目难度
+
题目历史正确率
+
知识点最近练习时间
```

自动推荐下一题。

# 七、数据库设计建议

建议至少存在以下表。

## `knowledge_point`

```sql
knowledge_point
-----------------------------
id
name
subject
section
chapter
default_role
status
created_at
updated_at
```

其中：

```text
id
```

直接使用现有：

```text
M1-H06-035
```

不建议重新随机生成 UUID 后把原 ID 丢掉。

可以：

```text
pk = 自增ID/UUID
knowledge_code = M1-H06-035
```

但 `knowledge_code` 必须唯一且长期稳定。

---

## `knowledge_alias`

不要把 aliases 塞成无法查询的普通长字符串。

建议单独建表：

```sql
knowledge_alias
-----------------------------
id
knowledge_point_id
alias
```

建立索引后，可以实现：

```text
用户搜索“挖洞高斯”
→ 返回“有瑕点的高斯公式”
```

---

## `question`

这里只举核心字段：

```sql
question
-----------------------------
id
subject
year
question_number
question_type
content
answer
analysis
difficulty
source
...
```

`difficulty` 应属于 **题目**，而不是知识点。

原因：

同一个知识点：

```text
拉格朗日中值定理
```

既可以出送分选择题，也可以出非常难的证明题。

因此不要写：

```text
knowledge_point.difficulty
```

---

## `question_knowledge`

这是整个设计的核心关系表。

题目和知识点是：

> **多对多关系**

建议：

```sql
question_knowledge
-----------------------------
question_id
knowledge_point_id
role
```

其中：

```text
role = core | auxiliary
```

例如：

```json
{
  "question_id": "2024-M1-20",
  "knowledge_id": "M1-H06-037",
  "role": "core"
}
```

同一道题还可以：

```json
{
  "question_id": "2024-M1-20",
  "knowledge_id": "M1-H06-039",
  "role": "auxiliary"
}
```

# 八、一道题应该绑定多少知识点

不要给一道题机械挂十几个标签。

推荐：

```text
1~3 个 core
+
0~3 个 auxiliary
```

典型情况：

### 示例1：有奇点曲面积分

```text
core:
有瑕点的高斯公式

auxiliary:
第二类曲面积分方向判断
第二类曲面积分对称性
```

### 示例2：二次型正交变换

```text
core:
正交变换化二次型为标准形
利用特征向量构造正交矩阵

auxiliary:
实对称矩阵正交对角化
```

### 示例3：条件期望题

```text
core:
全期望公式
协方差计算

auxiliary:
条件期望
```

# 九、不要做的事情

## 1. 不要自行重新拆知识点

例如不要看到：

```text
普通高斯公式
高斯公式补面法
有瑕点的高斯公式
```

就自作主张合并成：

```text
高斯公式
```

这会损失非常重要的题型信息。

---

## 2. 不要把步骤拆成知识点

例如不要创建：

```text
求偏导
代入坐标
整理式子
约分
计算行列式第二行
```

这些只是运算步骤。

---

## 3. 不要把一道特殊题变成一个知识点

例如：

```text
参数a=2时的高斯公式问题
```

绝对不应该成为知识点。

---

## 4. 不要根据名称字符串建立关系

必须使用 ID。

错误：

```text
question.knowledge = "有瑕点的高斯公式"
```

推荐：

```text
question_knowledge.knowledge_id = "M1-H06-035"
```

---

## 5. 不要随意修改已有 ID

已有知识点一旦绑定大量题目：

```text
M1-P01-011
```

就不能因为重新排序而变成：

```text
M1-P01-008
```

如果未来要重新展示排序，请增加：

```text
sort_order
```

不要改 identity。

---

# 十、版本升级规则

当前版本可以理解为：

```text
Math1 Knowledge Final 1.0
```

后续真实题库绑定时，如果发现遗漏，不要直接修改旧数据。

建议：

### 新增

增加新知识点，例如：

```text
M1-H06-045
```

并记录：

```text
introduced_version = 1.1
```

### 改名

ID 不变：

```text
M1-H06-035
```

只修改：

```text
name
```

旧名称放入：

```text
aliases
```

### 合并

例如 A 合并进 B：

不要删除 A。

建议：

```text
A.status = deprecated
A.merged_into = B.id
```

然后后台迁移题目关系。

# 十三、最重要的设计思想

请始终记住：

这不是一个“数学教材目录”。

而是：

> **一个为题库、知识诊断和自适应刷题设计的稳定知识点字典。**

它的核心价值不是“把数学知识全部列一遍”，而是让系统能够回答：

```text
这道题到底考了哪些具体能力？
```

以及：

```text
用户到底是哪一种题不会？
```

因此在开发过程中：

- 保持知识点 ID 稳定；
- 保持粒度稳定；
- 支持一题多知识点；
- 区分 core / auxiliary；
- 使用 aliases 解决不同叫法；
- 不轻易新增、删除或合并知识点；
- 题目难度属于题目，不属于知识点；
- 高频程度应该由真实题目统计得出，而不是人工拍脑袋。

```text
math1-knowledge-final.json
math1-knowledge-final.md
math1-knowledge-final.csv
```

5. 支持 core / auxiliary；
6. 支持 aliases 搜索；
7. 确保已有知识点 ID 不被改写；
8. 再开始实现题目绑定、专项刷题、统计和用户掌握度功能。

如果现有项目架构与这里建议的表结构不同：

> 可以调整实现方式，但必须保留上述数据语义和知识点身份稳定性。

不要为了迎合现有代码而把 469 个知识点重新压成几十个章节标签。

## 最终一句话

**这套文件是数学一题库的“知识坐标系”。**

题目是内容，知识点是坐标。

后续错题分析、专项刷题、学习进度、自适应推荐、真题统计，都应该围绕这套稳定坐标系构建。
