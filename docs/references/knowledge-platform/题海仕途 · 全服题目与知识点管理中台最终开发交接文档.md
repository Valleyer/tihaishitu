# 3. 数学一知识体系基本原则

当前正式数学一末级知识点共：

```text
469 个
```

其中：

```text
高等数学：198
线性代数：136
概率论与数理统计：135
```

这套知识点不是普通教材目录。

它的拆分原则是：

> 一个知识点尽量对应一类稳定题型，或者一种稳定解题方法。

例如不能只有：

```text
曲面积分
```

而会进一步区分：

```text
第二类曲面积分直接投影法
三合一投影法
普通高斯公式
高斯公式补面法
有瑕点的高斯公式
第一类斯托克斯公式
第二类斯托克斯公式
斯托克斯公式换面法
```

目标是未来可以回答：

> “这道题到底考了哪些能力？”

以及：

> “用户到底是哪一种题不会？”

# 4. KnowledgePoint 的稳定身份

知识点业务 ID 形如：

```text
M1-H06-035
```

含义：

```text
M1 = 数学一
H  = 高等数学
L  = 线性代数
P  = 概率论与数理统计
06 = 章节
035 = 章节内知识点编号
```

这些 ID 是知识点长期稳定身份。

不得因为：

- 改名
- 调整排序
- 修改章节显示顺序
- 数据库迁移

而改变。

但是当前项目大量逻辑要求 UUID。

因此本项目推荐采用：

```text
数据库内部 ID = UUID
稳定业务 ID = code
```

例如：

```text
id   = 9d7c... UUID
code = M1-H06-035
name = 有瑕点的高斯公式
```

其中：

```text
code UNIQUE NOT NULL
```

所有后台人工操作和导入导出均优先展示 `code`。

不要直接把 `M1-H06-035` 塞进当前必须是 UUID 的字段。

# 5. KnowledgePoint 必须脱离 QuestionBank

当前项目实际上还是：

```text
QuestionBank
 ├─ KnowledgePoint
 ├─ KnowledgePoint
 ├─ Question
 └─ Question
```

这种模型需要改变。

长期模型应当是：

```text
KnowledgePoint
      ↑
      │
      │ 多对多
      │
Question
```

而：

```text
QuestionBank / Collection
```

只是题目集合。

因此：

> KnowledgePoint 不再属于某一个 QuestionBank。

同一个：

```text
M1-H06-035 有瑕点的高斯公式
```

可以被：

- 1987 数一真题
- 2025 数一真题
- 模拟题
- 专项训练题
- 后续数学二题目
- 不同官方题集

中的题目共同引用。

绝不能复制多个同名知识点。

# 11. QuestionType 与 GradingMode 必须分离

不要继续把：

```text
题型
```

和：

```text
怎么判题
```

认为是一回事。

建议：

```text
question_type
```

表示原始题型：

```text
single_choice
multiple_choice
true_false
blank
solution
```

另外：

```text
grading_mode
```

表示判题方式：

```text
auto
self_assessment
```

再增加：

```text
presentation_type
```

表示玩家实际看到的交互形式，例如：

```text
single_choice
multiple_choice
true_false
self_assessment
```

这样可以出现：

### 原始选择题

```text
question_type = single_choice
presentation_type = single_choice
grading_mode = auto
```

### 原始填空题，游戏转换为选择题

```text
question_type = blank
presentation_type = single_choice
grading_mode = auto
```

### 原始解答题

```text
question_type = solution
presentation_type = self_assessment
grading_mode = self_assessment
```

### 不适合改造成选择题的复杂填空题

允许：

```text
question_type = blank
presentation_type = self_assessment
grading_mode = self_assessment
```

不要假定所有 blank 必须自动判题。

# 12. 填空题的设计

数学、408 中大量填空题适合转换成选择题。

这是允许的，并且属于游戏呈现方式调整。

例如原题：

```text
若 ……，则结果为 ______。
```

原始答案：

```text
1/2
```

数据库仍保存：

```text
question_type = blank

original answer = 1/2
```

游戏化呈现可以配置：

```text
A. -1/2
B. 1/2
C. 1
D. 2
```

其中：

```text
B
```

为正确选项。

因此 QuestionOption 应允许服务于：

> 原本是 blank、但游戏里按 choice 展示的题目。

不要因为游戏展示成选择题，就把：

```text
question_type
```

改成：

```text
single_choice
```

否则未来统计：

> 历年真题填空题出现次数

会产生错误。

---

# 13. 填空题干扰项

不要让服务器随便随机生成三个错误数字作为正式选项。

数学填空题干扰项应尽量对应：

- 常见符号错误
- 漏乘系数
- 常见公式误用
- 上下限错误
- 方差与标准差混淆
- 秩 / 维数误判
- 极限常见错误
- 典型计算失误

管理后台需要允许贡献者 / 审核者手工维护这些游戏化选项。

以后可以增加 AI 辅助生成干扰项。

但是 AI 生成结果仍然必须经过审核后才能发布。

本轮不要求实现 AI 生成。

# 14. 解答题必须成为正式可刷题型

数学和 408 解答题是重点。

不能因为无法自动批改，就排除在游戏之外。

原题必须完整保存并允许正式进入学习流程。

推荐流程：

```text
展示真题原题
        ↓
用户在纸上 / 草稿纸作答
        ↓
点击：
“我已完成，查看参考答案”
        ↓
显示：
标准答案
完整解析
知识点解析
        ↓
用户自行对照
        ↓
三个自评按钮
```

三个按钮：

```text
完整答对

部分正确

做错 / 不会
```

不要只设计：

```text
答对
答错
```

因为数学和 408 大题大量存在：

- 第一问对、第二问错
- 思路正确、计算错误
- 关键步骤正确但最终结果错误
- 算法思想正确但复杂度错误
- 网络题前两问正确、最后一问不会

必须保存 partial。

# 15. 自评判题数据结构

不要简单重新启用项目早期残留的：

```text
selfAssessment?: boolean
```

作为最终方案。

正式建立：

```text
grading_source
```

至少：

```text
automatic
self
```

自评结果：

```text
assessment
```

至少：

```text
correct
partial
wrong
```

推荐 Attempt / Result 支持：

```text
gradingMode

gradingSource

assessment
```

现有：

```text
correct: boolean | null
```

可以继续保留用于兼容旧 UI。

推荐语义：

```text
assessment = correct
→ correct = true

assessment = partial
→ correct = false

assessment = wrong
→ correct = false
```

但必须单独保存：

```text
assessment = partial
```

不能在数据库里永久丢失 partial 信息。

# 16. 自评题作答状态

自评题至少存在三个阶段：

```text
answering
revealed
graded
```

用户不能一进入题目就自动看到标准答案。

流程：

```text
answering
   ↓ 点击查看答案
revealed
   ↓ 选择自评
graded
```

服务器应保存状态。

推荐增加专门行为接口，例如：

```text
POST /games/{id}/answers/reveal

POST /games/{id}/answers/self-assess
```

或者采用与现有代码兼容性更好的等价设计。

不要强行把“查看答案”和“自评结算”塞进一个不可区分的请求。

---

# 17. 自评对现有游戏评分的影响

当前游戏活动按知识点首题决定得分。

该逻辑继续成立。

对于自评题：

```text
完整答对
```

等价于：

```text
本知识点首题正确
```

而：

```text
部分正确
做错/不会
```

均不算“首题完全正确”。

也就是说：

```text
partial
```

不能帮助县试 / 府试获得该知识点分数。

它应该像首次答错一样：

进入当前知识点的补漏 / 训练流程。

但学习历史必须区分：

```text
partial
wrong
```

不能简单混成完全相同的数据。

以后知识点 mastery 算法可以考虑给 partial 权重。

本轮不做复杂权重算法。

当前题海仕途主要是个人学习型游戏。

因此：

> 允许用户自评推动个人剧情和学习进度。

这是可以接受的。

```text
grading_source = self
```

- 全服排行榜

可以规定：

```text

```

不进入正式认证成绩。

因此现在不要把自评和服务器自动判题混成同一种可信度数据。

# 21. default_role 与 relation role 是两回事

KnowledgePoint 有：

```text
default_role
```

但它只是默认建议。

例如：

```text
条件期望
```

可能默认：

```text
auxiliary
```

但某道题如果主要考条件期望：

该题关系可以是：

```text
role = core
```

后台必须允许 relation role 覆盖 default_role。

不能写死。

# 22. QuestionBank 的长期语义

QuestionBank 不再拥有 Question 和 KnowledgePoint。

它逐渐变成：

```text
题目集合
```

建议长期结构：

```text
question_bank

question_bank_item
```

例如：

```text
question_bank_item
------------------
bank_id
question_id
sort_order
```

而不是继续依赖：

```text
question_item.bank_id
```

作为题目唯一身份。

但是当前游戏已经依赖旧 Bank DTO。

所以：

> 存储模型正确优先，现有游戏接口可以暂时通过 Projection / Adapter 输出旧 DTO。

不要为了重构数据库一次性推倒现有游戏。

# 23. 藏书阁与管理后台必须严格隔离

这是硬要求。


```text
个人私有
```

- 自己导题
- 自己建题
- 自己维护个人题集
- 收藏题目
- 组织私人练习

这些都不代表全服资源。

## 管理后台

新增：

```text
/manage
```

代表：

```text
全服资源管理
```

负责：

- 官方知识点
- 官方题目
- 历年真题
- 审核

允许：

# 71. 最核心的产品原则

请始终围绕以下几点实施：

### 1.

**知识点是稳定坐标，题目是内容。**

### 2.

**题目和知识点是多对多关系。**

### 3.

**原题是什么，就必须保存成什么。**

游戏呈现方式可以变化，但不能篡改原始题型。

### 4.

**数学和 408 大题不能因为自动判题困难而被舍弃。**

使用自评模式解决。

### 5.

**填空题可以游戏化转换成选择题。**

但必须保留其原始 blank 身份。

### 6.

**个人藏书阁与全服管理后台不是同一个系统层级。**

### 7.

**贡献者可以建设题库，但不能任意破坏知识坐标系。**

### 8.

**所有真正权限都由 Java 后端执行。**

### 9.

**现有游戏必须继续正常运行。**

### 10.

**不要为了本阶段做未来功能，但必须给未来留下正确的数据基础。**
